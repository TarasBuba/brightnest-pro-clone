# DAG Runner: Multi-Agent Workflow Orchestrator

Оркеструє виконання завдань за специфікацією Directed Acyclic Graph (DAG) (наприклад, за шаблоном [dag-spec-template.md](references/dag-spec-template.md)).

## ⚠️ Handoff Rule (ПРАВИЛО БЕЗШОВНОГО ПЕРЕХОДУ — MANDATORY)

Якщо план або специфікація (`implementation_plan.md`) містить паралельні хвилі (Multi-Agent DAG / Parallel Waves 1..N):
1. Головний агент (Root Orchestrator) **СУВОРО НЕ МАЄ ПРАВА** власноруч створювати або модифікувати файли модулів (`write_to_file` / `replace_file_content`) під час виконання паралельних хвиль.
2. Головний агент **ЗОБОВ'ЯЗАНИЙ** діяти виключно через інструмент `invoke_subagent`, призначаючи субагентам ізольовані завдання згідно з матрицею володіння файлами (*File Ownership Matrix*).
3. Головний агент відповідає виключно за:
   - Підготовку базових контрактів (Wave 0);
   - Запуск та контроль точок синхронізації (Sync Points / Quality Gates через `run_command`);
   - Інтеграцію та фінальний Red-Team аудит (Wave 3).

## 🚦 Mandatory Model Routing Rule (МАРШРУТИЗАЦІЯ МОДЕЛЕЙ)

При виклику `invoke_subagent` оркестратор **СУВОРО ЗОБОВ'ЯЗАНИЙ** явно вказувати параметр `Model` для кожного субагента:
- `Model: 'flash'` (або `'flash_lite'`) — обов'язково для паралельних виконавців (Wave 1..N) та модульного кодингу.
- `Model: 'pro'` — обов'язково для Wave 0 (контракти/типи) та Wave 3 (Red-Team Adversarial аудит).
- **СУВОРО ЗАБОРОНЕНО:** не вказувати `Model` або залишати `'inherit'` за замовчуванням для воркерів. Це призводить до розбалансування витрат або недостатньої глибини аудиту.

## 1. Контракт виконання DAG

1. **Аналіз графу (Decomposition & Task Graph):**
   - Визнач базову послідовну хвилю (Wave 0: Baseline / Contracts / Shared Types).
   - Визнач паралельні хвилі (Wave 1..N: Parallel Subtasks).
   - Встанови детерміновані точки синхронізації (Sync Points / Merge Gates) між хвилями.

2. **Матриця володіння файлами (File Ownership Matrix & Anti-Conflict Guarantee):**
   - Переконайся, що жодні два паралельні субагенти однієї хвилі не мають перетину у списку дозволених для запису файлів.
   - За наявності ризику *False Parallelism* (спільні файли/експорти) — винеси спільні інтерфейси у попередню послідовну хвилю (див. [false-parallelism-guide.md](references/false-parallelism-guide.md)).

3. **Маршрутизація моделей та бюджети токенів (Model Routing & Budgeting):**
   - Керуйся матрицею [model-routing-and-budget.md](references/model-routing-and-budget.md).
   - Зафіксуй граничний бюджет токенів та ліміт спроб (Iteration Budget) для кожного субагента.

4. **Ізоляція робочих просторів (Workspaces):**
   - Для паралельних субагентів використовуй `Workspace: 'branch'` (створення ізольованих git worktree/branch).
   - Для залежних інтеграційних задач використовуй `Workspace: 'inherit'`.

5. **Точки синхронізації (Sync Points) та верифікація:**
   - Після завершення кожної хвилі запусти детермінований верифікаційний ланцюг (`pnpm verify`, `npm test`, `cargo test` тощо).
   - Лише за 100% проходження верифікації переходь до наступної хвилі.
   - При збоях застосовуй правило Circuit Breaker: максимум 2 спроби автовиправлення перед ескалацією до людини.

6. **Фінальний Red-Team & Tech Debt Verifier (Adversarial Quality Gate):**
   - Запусти окремого субагента на сильній моделі (`Model: 'pro'`) з інструкціями `code-review` та `tech-debt-auditor` (навмисний пошук крайових дефектів, регресій, GIST/AI slop коментарів, RSC security leaks, порушень доступності за EAA та вимог стійкості).
   - Отримай фінальний вердикт `PASS` або перелік блокуючих дефектів.

7. **Підсумковий звіт (Cost & Telemetry Report):**
   - Надай структурований звіт: перелік виконаних хвиль, стан гейтів, тривалість, орієнтовні витрати токенів та журнал ухвалених рішень.
